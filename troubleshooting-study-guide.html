FLAGSHIP CASE

카카오클라우드 NPU 무료사용 후 인스턴스 전면 삭제에도 300만 원 폭탄 과금 사태

클라우드 자원 가시성 결여 & 계정 삭제 트러블슈팅
1 증상 (Symptom)
카카오클라우드 NPU 가속기 인스턴스를 무료 프로모션 기간 동안 사용한 후, 프로모션 종료 시점에 맞춰 콘솔에 접속하여 모든 인스턴스와 발급된 접속 키(키페어)를 완전히 삭제함.
그러나 익월 청구서 확인 시, 인스턴스가 전혀 없음에도 불구하고 300만 원 이상의 대규모 폭탄 과금이 등록된 신용카드로 청구되거나 발행되는 치명적 과금 사태 발생.
2 가설 (Hypothesis)
사용자가 UI 화면에서 '인스턴스'와 '키'만 지웠을 뿐, NPU 전용 하위 할당 자원(가속기 예약 풀, 백엔드 파티션, 전용 스토리지 볼륨)이 해제되지 않고 백그라운드에서 시간당 비용으로 지속 과금되고 있을 것이다.
특히 카카오클라우드는 통합 자원 과금 대시보드가 부재하고 보이지 않는 숨은 설정들이 많아, 사용자가 콘솔 화면에서 잔여 자원을 인지하거나 수동으로 찾아 지우는 것이 구조적으로 불가능했을 것이다.
3 검증 (Verification)
1. 콘솔 UI 점검: 인스턴스 및 키페어 목록은 이미 0건으로 비어있어, 사용자가 수동으로 삭제할 항목을 UI에서 전혀 찾을 수 없음.
2. 고객센터 긴급 소명 문의: 청구 내역 대조 결과, 인스턴스는 삭제되었으나 콘솔 UI에 노출되지 않는 NPU 백엔드 할당 설정 및 예약 리소스들이 여전히 활성화(Active) 상태로 남아 시간당 과금을 유발하고 있었음이 공식 검증됨.
4 조치 (Action)
[핵심 트러블슈팅 해법]
사용자가 개별 설정을 콘솔에서 찾아 지우려 애쓰는 방식은 불가능하다고 판단하고, 고객센터에 공식 긴급 요청으로 "계정 탈퇴 및 계정에 귀속된 모든 NPU 구독과 하위 설정 전면 강제 삭제(Total Account Decommissioning)"를 요청함.

⚠️ 충격적인 실무 현실: 카카오클라우드 기술지원팀 및 운영진 자체도 통합 대시보드가 없고 보이지 않는 설정들이 복잡하게 얽혀 있어, 그들이 고객의 모든 잔여 설정을 수동으로 추적하여 완전히 삭제하는 데만 수 주가 소요되었으며, 다음 달이 되어서야 모든 삭제 처리가 완료됨.
5 결과 (Result)
카카오클라우드 최고위 기술지원팀의 백엔드 수동 삭제 및 계정 완전 폐쇄가 완료되어 비정상 과금 파이프라인이 원천 차단됨.
사용자가 무료체험 종료 시점에 인스턴스를 정상 삭제했던 로그와 콘솔 대시보드 가시성 부재를 입증하여, 300만 원 이상의 부당 청구액 전액 청구 취소 및 감면 조치 확정.
6 재발 방지 (Prevention)
1. 신용카드 사전 등록 절대 주의: NPU/GPU 고가 자원 무료 프로모션 이용 전 한도가 무제한인 신용카드를 무분별하게 등록하지 말고, 잔액이 제한된 체크카드나 가상 결제수단을 활용하거나 사용 직후 결제수단을 삭제/정지함.
2. 대시보드 부재 클라우드 이용 원칙: 통합 모니터링 대시보드가 없는 클라우드는 단순 콘솔 인스턴스 삭제를 맹신하지 말고, 무료 기간 종료 전 반드시 고객센터에 '계정 삭제 및 전 자원 완전 삭제 요청'을 공식 접수하여 잔여 0건 확약을 받는 프로세스를 준수함.
💡 핵심 엔지니어링 교훈 (Key Takeaway)

"보이지 않는 리소스가 가장 무서운 과금의 주범이다." 인스턴스를 지워도 하위 예약 풀이 살아남는 고가 NPU/GPU 자원은, 대시보드가 없다면 고객센터를 통한 계정 전면 삭제 요청만이 유일하고 확실한 해결책입니다.

⚠️ 흔히 하는 치명적 실수 (Common Pitfall)

"화면에서 인스턴스를 지웠으니 요금이 안 나오겠지"라고 방심하고 방치하는 것입니다. 클라우드는 백엔드에 얽힌 종속 자원이 남아있으면 매시간 과금 폭탄을 투하합니다.

CASE 01

SSH 22번 포트 접속 타임아웃 및 /32 단일 공인 IP 격리

L3/L4 Stateful Firewall (Security Group)
1 증상 (Symptom)
관리자 터미널에서 EC2 원격 접속 시도 시 응답이 멈추며 1~2분 후 Operation timed out 오류가 발생하고 접속이 강제 종료됨.
Terminal Error
$ ssh -i ~/.ssh/mission-key.pem ubuntu@54.180.1.48
ssh: connect to host 54.180.1.48 port 22: Operation timed out
2 가설 (Hypothesis)
가정/카페 ISP 통신사의 유동 IP 할당 특성으로 인해 관리자 로컬 PC의 공인 IP가 변경되었으나, AWS 보안 그룹(mission-web-sg) 인바운드 규칙에는 과거 공인 IP(/32)가 등록되어 있어 신규 IP 패킷이 방화벽에서 Drop되고 있을 것이다.
3 검증 (Verification)
외부 IP 조회 서비스(ipify)로 확인한 현재 공인 IP와 AWS CLI로 조회한 보안 그룹 인바운드 IP 대역을 교차 대조함.
AWS CLI Inspection
# 1. 현재 관리자 공인 IP 확인
$ curl -s https://api.ipify.org
121.135.181.35

# 2. 보안 그룹에 등록된 허용 IP 확인
$ aws ec2 describe-security-groups --group-names mission-web-sg \
--query 'SecurityGroups[0].IpPermissions[?ToPort==`22`].IpRanges[0].CidrIp' --output text
211.234.56.78/32 <-- 불일치 확인 (원인 확정!)
4 조치 (Action)
기존 만료된 규칙을 즉시 회수(Revoke)하고, 확인된 현재 단일 공인 IP(/32)를 새롭게 인가(Authorize)함.
Remediation CLI
# 1. 기존 규칙 회수
$ aws ec2 revoke-security-group-ingress --group-id sg-0a1b2c3d4e5f6g7h8 \
--protocol tcp --port 22 --cidr 211.234.56.78/32

# 2. 현재 공인 IP(/32) 단독 허용 등록
$ MY_IP="$(curl -s https://api.ipify.org)/32"
$ aws ec2 authorize-security-group-ingress --group-id sg-0a1b2c3d4e5f6g7h8 \
--protocol tcp --port 22 --cidr "$MY_IP"
5 결과 (Result)
규칙 갱신 즉시 ssh -i mission-key.pem ubuntu@54.180.1.48 실행 시 0.5초 이내에 정상 로그인 프롬프트 ubuntu@ip-10-0-1-X:~$ 획득 성공. 비인가 IP는 원천 Drop 유지.
6 재발 방지 (Prevention)
1. scripts/setup-aws.sh에 배포 시점 공인 IP 자동 감지 주입 로직을 내장함.
2. 편의를 위해 22번 포트를 전 세계(0.0.0.0/0)로 여는 행위를 보안 감사 규정으로 엄격히 금지함.
💡 핵심 학습 포인트 (Key Takeaway)

보안 그룹(Security Group)은 상태 저장(Stateful) 방화벽이므로, 인바운드 룰이 맞지 않으면 아웃바운드 허용 여부와 무관하게 SYN 패킷 단계에서 Silent Drop(타임아웃) 처리됩니다.

⚠️ 흔히 하는 실수 (Common Pitfall)

SSH가 안 된다고 무심코 0.0.0.0/0으로 열어버리면, 수 분 만에 전 세계 봇넷(Botnet)의 무차별 대입(Brute-force) 타깃이 되어 서버가 즉시 장악될 수 있습니다. 반드시 /32 단일 IP를 고수해야 합니다.

CASE 02

보안 그룹 80 오픈 후 외부 웹 접속 불가 (IGW 기본 라우트 누락)

VPC Networking & Route Table
1증상 (Symptom)
EC2 내부에서 curl -I http://localhost는 200 OK를 반환하며 Nginx가 정상 실행 중이나, 외부 브라우저에서 http://54.180.1.48 접속 시 무한 로딩 후 ERR_CONNECTION_TIMED_OUT 발생.
2가설 (Hypothesis)
보안 그룹 인바운드 규칙에는 Port 80이 0.0.0.0/0으로 열려 있으나, 서브넷 라우팅 테이블(Route Table)에 인터넷 게이트웨이(mission-igw)로 향하는 기본 라우트(0.0.0.0/0)가 누락되어 패킷 왕복이 차단되었을 것이다.
3검증 (Verification)
서브넷에 연결된 라우팅 테이블 경로를 조회하여 기본 인터넷 라우트 존재 여부를 검사함.
Route Table Inspection
$ aws ec2 describe-route-tables --filters "Name=association.subnet-id,Values=subnet-0123456789abcdef0" \
--query 'RouteTables[0].Routes' --output json
[
{ "DestinationCidrBlock": "10.0.0.0/16", "GatewayId": "local", "State": "active" }
] <-- 0.0.0.0/0 ➔ mission-igw 라우트가 없음! (원인 확정)
4조치 (Action)
라우팅 테이블에 외부 인터넷 전체(0.0.0.0/0)를 인터넷 게이트웨이(mission-igw)로 전달하는 라우트 엔트리를 추가함.
Add Default Route
$ aws ec2 create-route --route-table-id rtb-0123456789abcdef0 \
--destination-cidr-block 0.0.0.0/0 \
--gateway-id igw-0123456789abcdef0
{ "Return": true }
5결과 (Result)
명령 실행 즉시 외부 브라우저 새로고침 시 "I Like AWS" 메인 대시보드가 정상 출력되며, curl -sI http://54.180.1.48 ➔ HTTP/1.1 200 OK 정상 반환 확인.
6재발 방지 (Prevention)
퍼블릭 서브넷 프로비저닝 스크립트 작성 시 [VPC 생성 ➔ IGW 생성 및 Attach ➔ 라우팅 테이블 0.0.0.0/0 등록 ➔ 서브넷 연결]을 원자적(Atomic) 트랜잭션으로 구성하여 단계 누락을 방지함.
💡 핵심 학습 포인트 (Key Takeaway)

VPC에서 인스턴스가 공인 IP를 가지고 있더라도, 서브넷 라우팅 테이블에 0.0.0.0/0 ➔ IGW 경로가 없으면 외부 통신이 불가능한 "가짜 퍼블릭 서브넷" 상태가 됩니다.

⚠️ 흔히 하는 실수 (Common Pitfall)

보안 그룹만 오픈하고 웹 접속이 안 된다며 Nginx 재시작을 반복하는 실수가 흔합니다. 외부 연결 문제는 항상 SG(방화벽) + Route Table(경로) 두 축을 함께 점검해야 합니다.

CASE 03

메인 웹은 정상이나 /health에서 404 Not Found (Nginx default 충돌)

L7 Application Layer (Nginx Virtual Host)
1증상 (Symptom)
브라우저에서 http://54.180.1.48/ 접속 시 메인 웹페이지는 잘 열리지만, 로드밸런서용 헬스체크 http://54.180.1.48/health 호출 시 404 Not Found가 발생함.
2가설 (Hypothesis)
Ubuntu apt로 Nginx 설치 시 자동 활성화되는 기본 가상 호스트(/etc/nginx/sites-enabled/default)가 포트 80의 기본 서버(default_server)로 우선 등록되어, 사용자가 추가한 커스텀 location 블록이 무시되고 있을 것이다.
3검증 (Verification)
sudo nginx -T로 가상 호스트 우선순위와 실제 참조 root 디렉토리를 덤프 분석함.
Nginx Configuration Dump
$ sudo nginx -T | grep -E "(server_name|listen|root)"
# /etc/nginx/sites-enabled/default:
listen 80 default_server;
root /var/www/html; <-- 여기에 health 파일이 없음!

# /etc/nginx/conf.d/web.conf:
listen 80; <-- default_server에 밀려 404 발생 확인!
4조치 (Action)
기본 default 사이트 심볼릭 링크를 제거하고, 명시적인 /health 고정 응답 location 블록을 구성한 뒤 Nginx를 리로드함.
Fix Nginx Configuration
# 1. 기본 default 가상 호스트 비활성화
$ sudo rm -f /etc/nginx/sites-enabled/default

# 2. 커스텀 location 블록 반영 (/etc/nginx/conf.d/web.conf)
location /health {
default_type text/plain;
return 200 'OK\n';
}

# 3. 문법 검사 및 무중단 리로드
$ sudo nginx -t && sudo systemctl reload nginx
5결과 (Result)
curl -i http://localhost/health 실행 시 HTTP/1.1 200 OK 응답 및 페이로드 "OK" 정상 수신. 브라우저에서도 즉시 "OK" 텍스트 렌더링 확인.
6재발 방지 (Prevention)
배포 자동화 스크립트(scripts/setup-aws.sh)에 Nginx 설치 직후 sites-enabled/default 파일을 선제 삭제하는 루틴을 표준화함.
💡 핵심 학습 포인트 (Key Takeaway)

Nginx에서 default_server 지시자는 매칭되는 호스트명이 없을 때 모든 트래픽을 가로채는 포트 점유자 역할을 하므로, 신규 가상호스트 구축 시 기본 설정을 반드시 정리해야 합니다.

⚠️ 흔히 하는 실수 (Common Pitfall)

설정 파일만 편집하고 systemctl reload nginx를 누락하거나, nginx -t 사전 검증 없이 재시작하여 웹 서비스 전체가 다운(Active: failed)되는 사고를 주의해야 합니다.

CASE 04

IAM 최소권한 RunInstances 권한 부족 및 피보팅(횡적 침투) 차단

Cloud Security Governance (IAM Least Privilege)
1증상 (Symptom)
실습 전용 배포 사용자(mission-deployer)로 CLI 명령을 통해 인스턴스 생성을 시도할 때 UnauthorizedOperation 권한 오류가 발생하며 생성이 중단됨.
IAM Permission Error
$ aws ec2 run-instances --image-id ami-0462a9141...
An error occurred (UnauthorizedOperation) when calling the RunInstances operation:
You are not authorized to perform this operation.
2가설 (Hypothesis)
IAM 정책에 ec2:RunInstances 액션만 등록되어 있고, EC2 생성 시 백그라운드에서 동반 호출되는 부속 리소스(EBS 볼륨 생성 ec2:CreateVolume, 서브넷 참조, 태그 생성 ec2:CreateTags) API 권한이 누락되었을 것이다.
3검증 (Verification)
AWS STS 디코딩 명령어로 거부된 메시지를 디코딩하여 정확히 어떤 부속 API 액션이 Deny되었는지 파악함.
Decode Authorization Message
# 디코딩 결과 확인
"action": "ec2:CreateVolume", "resource": "arn:aws:ec2:ap-northeast-2:...:volume/*"
➔ EBS 볼륨 생성 API 권한이 빠져있음을 정확히 진단!
4조치 (Action)
편하다고 AdministratorAccess를 주는 대신, iam/minimal-deployer-policy.jsonl 정책에 필수 연관 EC2/VPC API만 정밀 추가하고, 무관한 S3, RDS, DynamoDB, IAM 권한은 명시적 Deny(Explicit Deny)로 완벽 격리함.
Minimal Policy JSON Structure
"Statement": [
{ "Effect": "Allow", "Action": ["ec2:RunInstances", "ec2:CreateVolume", "ec2:CreateTags", ...] },
{ "Effect": "Deny", "Action": ["s3:*", "rds:*", "dynamodb:*", "iam:*"], "Resource": "*" }
]
5결과 (Result)
정책 갱신 후 aws ec2 run-instances 정상 성공(인스턴스 생성 완료). 동시에 웹서버에서 탈취된 키로 aws s3 ls 시도 시 AccessDenied로 즉각 차단되어 피보팅(횡적 침투) 공격 원천 방어 성공.
6재발 방지 (Prevention)
"배포가 안 된다고 관리자 권한(Admin)을 주는 행위"를 금지하고, 정책 정의 파일을 Git으로 형상 관리하여 최소 권한(Least Privilege) 원칙을 상시 준수함.
💡 핵심 학습 포인트 (Key Takeaway)

EC2 인스턴스는 단독으로 생성되지 않으며 반드시 EBS 볼륨, 서브넷, 보안 그룹, 태그 등의 리소스와 결합됩니다. 따라서 최소 권한 설계 시 연관 리소스 액션을 반드시 패키지로 선별 허용해야 합니다.

⚠️ 흔히 하는 실수 (Common Pitfall)

권한 에러를 만났을 때 귀찮아서 AdministratorAccess를 부여하는 습관은 사내 데이터 유출 및 수천만 원대 비트코인 채굴 악용 사고의 제1 원인입니다.

🧠 자가 점검 퀴즈 (Self-Check Quiz)
Q. 웹 서버 인스턴스에 탄력적 IP(EIP)를 할당하고 보안 그룹에서 80번 포트를 0.0.0.0/0으로 개방했음에도 불구하고, 외부 인터넷에서 웹 접속이 되지 않고 타임아웃이 발생할 때 가장 먼저 의심해야 할 네트워크 컴포넌트는 무엇일까요?
정답: 서브넷의 라우팅 테이블(Route Table)에 등록된 0.0.0.0/0 ➔ Internet Gateway(IGW) 기본 라우트 누락!

보안 그룹(방화벽)이 열려 있어도 라우팅 테이블에 인터넷 관문(IGW)을 가리키는 경로가 설정되어 있지 않으면 패킷이 서브넷 밖으로 나가지 못합니다. (트러블슈팅 사례 2번 참조)
