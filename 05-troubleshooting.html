5. 트러블슈팅 보고서 요약

단순 1건 제출 기준을 넘어, 실제 카카오클라우드 NPU 구독 후 인스턴스/키 전면 삭제에도 발생한 300만 원 폭탄 과금 사태와 고객센터 계정 전면 삭제 요청을 통한 최종 해결 사례를 `증상 ➔ 가설 ➔ 검증 ➔ 조치 ➔ 결과 ➔ 재발방지` 6단계 표준 절차로 완벽히 구조화하여 수록했습니다.

🎓 6단계 시각 학습자료 & 자가점검 퀴즈 대시보드 바로가기

🔥 [핵심 실제 사례] 카카오클라우드 NPU 무료사용 후 인스턴스 전면 삭제에도 300만 원 폭탄 과금 사태

클라우드 과금 참사 & 계정 삭제
1. 증상 카카오클라우드 NPU 가속기 서비스를 무료사용 기간 동안 쓴 뒤 콘솔에서 모든 인스턴스와 키(키페어)를 전면 삭제했으나, 익월 청구서에 300만 원 이상의 대규모 폭탄 과금이 청구되는 치명적 사태 발생
2. 원인 가설 사용자가 콘솔 UI에서 '인스턴스'와 '키'만 지웠을 뿐, NPU 할당 단위의 백엔드 예약 풀, 가속기 파티션, 전용 스토리지 등 콘솔 대시보드에 보이지 않는 숨겨진 하위 설정들이 해제되지 않고 백그라운드에서 시간당 비용으로 지속 과금 중일 것
3. 검증 방법 카카오클라우드는 통합 리소스 가시성 대시보드가 부재하여 콘솔 UI 상에서 잔여 자원을 찾을 수 없음. 고객센터 문의 결과 인스턴스는 지워졌으나 보이지 않는 NPU 백엔드 종속 설정들이 여전히 활성화(Active) 상태로 누적 과금을 유발하고 있음을 공식 확인
4. 조치 내용 [핵심 트러블슈팅] 사용자가 개별 리소스를 수동 삭제하는 것이 불가능하므로, 고객센터에 긴급 요청으로 "계정 탈퇴 및 계정 내 모든 NPU 구독/하위 설정 전면 강제 삭제"를 요청.
⚠️ 카카오클라우드 기술지원팀 자체도 대시보드가 없고 보이지 않는 설정이 많아, 고객센터 엔지니어들이 모든 설정을 수동 추적하여 완전히 삭제하는 데만 수 주가 소요되어 다음 달이 되어서야 모든 삭제가 완료됨
5. 최종 결과 고객센터 엔지니어링팀의 백엔드 수동 삭제 및 계정 완전 폐쇄로 비정상 과금 파이프라인 원천 차단. 정상 인스턴스 삭제 시도 및 콘솔 가시성 결여 소명으로 300만 원 이상 부당 청구액 전액 청구 취소 및 감면 조치 완료
6. 재발 방지 1. 신용카드 사전 등록 주의: 클라우드 NPU/GPU 고가 자원 구독 전 신용카드 무분별 등록을 피하고, 한도 제한 카드 사용.
2. 대시보드 부재 클라우드 이용 원칙: 대시보드가 없는 클라우드는 단순 인스턴스 삭제를 맹신하지 말고, 무료 기간 종료 전 고객센터에 '계정 삭제 및 전 자원 완전 삭제'를 공식 접수하는 프로세스 확립

🚨 사례 1. SSH 접속 타임아웃 및 /32 공인 IP 격리

네트워크 / 방화벽
1. 증상 ssh -i mission-key.pem ubuntu@54.180.1.48 실행 시 Operation timed out 발생하며 원격 세션 연결 불가
2. 원인 가설 로컬 인터넷 ISP의 유동 공인 IP가 변경되어, 보안 그룹에 등록된 기존 22번 포트 허용 IP(/32)와 불일치
3. 검증 방법 curl -s https://api.ipify.org로 조회된 실제 내 공인 IP와 aws ec2 describe-security-groups 상의 CidrIp 대역 비교
4. 조치 내용 변동된 현재 공인 IP(121.135.181.35/32)로 보안 그룹 SSH 인바운드 규칙을 즉시 갱신 반영
5. 최종 결과 인가되지 않은 제3자 IP의 접근은 원천 차단(Drop) 유지되며, 관리자 단독 SSH 정상 접속 100% 복구
6. 재발 방지 scripts/setup-aws.sh에 자동 IP 감지 주입 로직을 탑재하고, 절대 0.0.0.0/0 오픈을 하지 않는 정책 수립

🌐 사례 2. 보안 그룹 80 오픈 후에도 외부 웹 접속 불가

VPC 라우팅
1. 증상 인스턴스 내부 localhost:80은 200 OK이나, 외부 브라우저 접속 시 무한 로딩 후 타임아웃
2. 원인 가설 보안 그룹만 오픈되고, 퍼블릭 서브넷의 라우팅 테이블에 인터넷 게이트웨이(IGW) 경로가 누락됨
3. 검증 방법 aws ec2 describe-route-tables 확인 결과 10.0.0.0/16 local 경로만 존재하고 기본 라우트 결여
4. 조치 내용 0.0.0.0/0 ➔ mission-igw 라우팅 엔트리를 라우팅 테이블에 등록 및 서브넷 바인딩 완료
5. 최종 결과 외부 브라우저에서 http://54.180.1.48 즉각적인 200 OK 렌더링 확인
6. 재발 방지 네트워크 배포 스크립트 작성 시 IGW 연결과 0.0.0.0/0 라우트 등록을 단일 트랜잭션으로 묶어 실행

⚙️ 사례 3. 메인은 정상이나 /health에서 404 Not Found

Nginx 웹 서버
1. 증상 GET /는 정상 응답하나 GET /health 호출 시 404 Not Found 에러 반환
2. 원인 가설 Ubuntu 패키지 매니저가 자동 생성한 Nginx 기본 가상 호스트(sites-enabled/default)가 80포트를 선점
3. 검증 방법 nginx -T 덤프 확인 시 default 사이트 블록이 커스텀 /health location 블록보다 우선순위 점유
4. 조치 내용 기본 default 설정 파일을 비활성화하고, 전용 location /health { return 200 'OK\n'; } 블록 적용
5. 최종 결과 curl -i http://localhost/health 호출 시 HTTP/1.1 200 OK 및 "OK" 문자열 완벽 수신
6. 재발 방지 Nginx 프로비저닝 스크립트에 rm -f /etc/nginx/sites-enabled/default 선제 삭제 로직 강제화

🔑 사례 4. IAM 최소권한 RunInstances API 오류 및 격리

IAM 보안
1. 증상 mission-deployer 계정으로 인스턴스 실행 시 UnauthorizedOperation 권한 거부 발생
2. 원인 가설 ec2:RunInstances 권한만으로는 인스턴스에 동반되는 EBS 볼륨 생성 및 서브넷/보안그룹 바인딩 액션 불능
3. 검증 방법 AWS CloudTrail 이벤트 로그에서 실패한 인코딩 에러 메시지 디코딩 분석
4. 조치 내용 필수 연관 리소스(EBS 볼륨, 보안그룹, 네트워크 인터페이스) 권한을 선별 허용하고, S3/RDS 등은 명시적 Deny 처리
5. 최종 결과 AdministratorAccess 없이도 EC2/VPC 배포를 완벽 수행하며 최소권한(Least Privilege) 원칙 100% 달성
6. 재발 방지 iam/minimal-deployer-policy.jsonl 정책 파일을 Git으로 형상 관리하여 임의 권한 확대 원천 차단
