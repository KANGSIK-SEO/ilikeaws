Amazon Web Services 환경에서 웹 서비스 인프라를 구축할 때 필수적으로 이해해야 하는 5대 핵심 네트워크 컴포넌트(VPC, Subnet, IGW, EC2, SG)의 구조와, 외부 인터넷 클라이언트에서 실제 Nginx 웹 애플리케이션으로 이어지는 패킷 인바운드/아웃바운드 흐름을 완벽히 마스터할 수 있는 교육용 명세서입니다.

5대 핵심 구성 요소 상세 명세 및 설계 원리

각 컴포넌트의 식별자, IP 대역, 격리 역할 및 엔지니어링 체크포인트

COMPONENT 1 Network Isolation

Virtual Private Cloud (VPC)

서울 리전(ap-northeast-2) 내에 CIDR 10.0.0.0/16(총 65,536개 사설 IP)의 전용 사설망을 구축하여 다른 고객 및 공용 인터넷과 논리적으로 완벽히 격리된 독립 가상 네트워크를 제공합니다.

식별자: mission-vpc 대역: 10.0.0.0/16
COMPONENT 2 Subnet Partition

Public Subnet (퍼블릭 서브넷)

가용영역 ap-northeast-2a에 CIDR 10.0.1.0/24(가용 IP 251개)를 할당했습니다. AWS가 예약한 5개 IP를 제외한 대역을 웹 서버 및 관문 서비스에 배정하며 자동 공인 IP 매핑을 활성화했습니다.

식별자: mission-public-subnet AZ: ap-northeast-2a
COMPONENT 3 Edge Gateway

Internet Gateway (IGW)

VPC와 인터넷을 연결하는 완전 관리형, 고가용성, 수평 확장형 양방향 통신 관문입니다. 인스턴스의 프라이빗 IP와 공인 IP 간의 1:1 네트워크 주소 변환(NAT)을 수행하여 병목 없이 패킷을 라우팅합니다.

식별자: mission-igw 연결: VPC Attached
COMPONENT 4 Virtual Firewall

Security Group (보안 그룹)

인스턴스 단위의 상태 저장(Stateful) 가상 방화벽입니다. HTTP 80은 0.0.0.0/0(전체) 오픈하고, SSH 22는 관리자 단일 IP(/32)로 제한하여 0-65535 전체 포트 침투를 원천 폐쇄(Default Deny)했습니다.

그룹명: mission-web-sg 동작: Stateful Filter
COMPONENT 5 Compute & Static IP

EC2 Instance & Elastic IP

프리티어 규격인 t2.micro(Ubuntu 22.04 LTS, 8GiB gp3)에 Nginx 1.x를 실행하고, 인스턴스 재부팅 후에도 공인 IP가 유지되도록 탄력적 고정 IP(54.180.1.48)를 1:1 바인딩했습니다.

인스턴스: mission-web-server 고정IP: 54.180.1.48
🚀

외부 → 서비스 인바운드 트래픽 흐름 (7단계 패킷 여정)

브라우저 요청이 인스턴스 커널을 거쳐 클라이언트로 반환되기까지의 End-to-End 라이프사이클

STEP 1
🌐 클라이언트 요청
사용자가 브라우저나 curl에서 http://54.180.1.48:80을 호출하여 TCP SYN 패킷을 공용 인터넷망으로 송신합니다.
STEP 2
🔀 Internet Gateway
AWS 엣지 백본망을 통해 패킷이 mission-igw에 도달하고, 목적지 EIP를 VPC 내부 인스턴스 사설 IP로 변환(Destination NAT)합니다.
STEP 3
📋 Route Table 조회
VPC 라우터가 서브넷 라우팅 테이블(mission-rtb)을 참조하여 목적지 10.0.1.0/24가 속한 퍼블릭 서브넷으로 패킷을 포워딩합니다.
STEP 4
🛡️ Security Group 검사
mission-web-sg의 인바운드 규칙을 검사합니다. 포트 80은 0.0.0.0/0 허용 규칙에 매칭되므로 패킷 인입을 인가(Allow)합니다.
STEP 5
🖥️ EC2 & Nginx 수신
가상 네트워크 인터페이스(eth0)를 거쳐 리눅스 커널이 패킷을 수신하고, 포트 80을 리스닝 중인 Nginx 웹서버 데몬으로 전달합니다.
STEP 6
📄 웹 애플리케이션 응답
Nginx가 요청 URL(/ 또는 /health)에 해당하는 정적 HTML 또는 "OK" 문자열과 함께 HTTP/1.1 200 OK 헤더를 생성합니다.
STEP 7
↩️ Stateful 자동 반환
보안 그룹의 상태 저장(Stateful) 특성으로 인해, 인바운드로 승인된 세션의 응답 트래픽은 아웃바운드 규칙에 무관하게 IGW를 거쳐 클라이언트에게 즉시 회신됩니다.
🔄 인스턴스 내부 ➔ 외부 인터넷 아웃바운드 통신 흐름 (NAT)

EC2 내부에서 패키지 업데이트(apt update)나 외부 API 연동(curl https://example.com)을 호출할 때의 패킷 경로:

1. EC2 패킷 생성 ➔ 2. Route Table (0.0.0.0/0) ➔ 3. mission-igw (Source NAT) ➔ 4. 외부 인터넷 서버 수신 ➔ 5. HTTP/2 200 OK 응답 회신
⚖️

Security Group(네트워크 방화벽) vs IAM(권한 관리) 심층 비교

클라우드 다계층 방어(Defense-in-Depth)를 구성하는 두 보안 축의 핵심 동작 차이

구분 항목 🛡️ Security Group (보안 그룹) 🔑 IAM (Identity and Access Management)
보호 대상 네트워크 패킷 / 데이터 전송 계층 (L3/L4) AWS 클라우드 제어 플레인 / Management API 호출
제어 기준 프로토콜(TCP/UDP/ICMP), 포트(80, 22), IP CIDR 블록 리소스 ARN, Action(허용/거부 API), Principal(사용자/역할)
상태 유지 (State) Stateful (인바운드 허용 시 아웃바운드 자동 통과) Stateless (매 API 요청마다 정책 전수 평가)
기본 정책 Default Deny (인바운드 명시적 허용 없으면 드롭) Default Deny (명시적 Allow 필요, Explicit Deny 최우선)
본 프로젝트 적용 • HTTP 80: 0.0.0.0/0 전 세계 오픈
• SSH 22: 관리자 공인 IP(/32) 단독 허용
• 미사용 전체 포트(0-65535) 차단 		• AdministratorAccess 전면 배제
• EC2/VPC 프로비저닝 전용 화이트리스트 적용
• S3, RDS, DynamoDB, IAM 명시적 Deny 격리

🧠 아키텍처 핵심 자가 점검 퀴즈

Q. 외부 사용자가 http://54.180.1.48:80으로 접속할 때, 보안 그룹의 아웃바운드 규칙에 포트 80이 허용되어 있지 않더라도 브라우저로 200 OK 웹페이지가 정상 회신되는 기술적 원리는 무엇일까요?

정답: 보안 그룹(Security Group)의 '상태 저장(Stateful)' 특성 때문입니다!

보안 그룹은 들어오는 패킷의 TCP 연결 상태(Connection Tracking)를 메모리에 기억합니다. 따라서 인바운드 규칙에 의해 허용된 요청에 대한 응답 트래픽(Return Traffic)은 아웃바운드 규칙에 상관없이 방화벽을 자동으로 통과하여 클라이언트에 전달됩니다. (반면 네트워크 ACL은 Stateless이므로 인바운드와 아웃바운드 양쪽 모두 규칙이 필요합니다.)
